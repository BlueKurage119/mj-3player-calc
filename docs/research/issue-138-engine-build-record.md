## 2. D-1a 測定(T=18、Worker 内の計算時間。冷。環境: Intel Core i7-9750H・macOS・headless Chrome 157)

13枚入力、向聴別の中央値の中央値(ms)。M=1 の S3 は 1手あたり 3〜10 回、M=2 の S2・S3 は 1回だけ測った。M=2 は S2 の3手・S3 の2手に限る(測定に数時間かかるため)。

| 構成 | 1向聴 | 2向聴 | 3向聴 | 3向聴の状態数(中央) |
| --- | --- | --- | --- | --- |
| A(手替わりなし) | 22 | 72 | 225 | 230 |
| B′ M=0 | 22 | 76 | 273 | 230 |
| B′ M=1 | 218 | 1,975 | 10,780 | 12,506 |
| B′ M=2 | 3,607 | 25,776(3手) | 361,607(2手) | 246,265 |

- 開始向聴ごとに中央値 ≤ 1,000 ms を満たす最大の M は、1向聴=1、2向聴=0、3向聴=0。M=0 は全手で最悪1回が 700 ms 未満
- 状態数は S3 で M=1 が約 55 倍、M=2 が約 1,600 倍
- 期待値の増分(手ごとの相対増の中央値、前段階比): B′ M=0/A は 1向聴 0%・2向聴 +5.6%・3向聴 +3.6%。B′ M=1/M=0 は +14.5%・+28.7%・+81.0%。M=0 は手替わりの価値を大きく過小評価する
- B′ と B′+戻しの差(Q16): 状態数は M=0・1 で30手とも同一、期待値差は最大 +2 点(+0.18%)、時間は誤差。M=2 のみ状態が 2〜5% 増える。後退案は不要と判断
- 14枚入力(C-01〜09。牌姿と候補ごとの向聴は `bench/engine/hands.ts` 先頭): 13枚入力より数倍遅く、M=0 の既定でも C-05 が約 7 s、C-07 が約 4.3 s
- Q18(共通 s_ref と対案S): 対案Sは状態数 +2〜7%、時間は同等、最適 ev は全手で共通以下、推奨初打は8手中5手で変わる(M=0・1とも)。A-5c の MC(16本)は両案とも 4σ 以内。T=3 の制限なしモデルとの比較(C-02・04・06・08)で、共通 s_ref は制限なしと完全一致、対案Sは向聴の良い候補の ev が低下(C-02 平均 −7.9点、C-04 −6.6点)。オーナーが共通 s_ref に確定

## 5. 設計との差異(最終)

1. A-5d(2): 戻し先が維持だけでも到達できるため、「戻しでしか到達しない」検査を外し `backtrack_edge_count > 0` の検査にした(設計第14版に反映)
2. A-4d: 手を S3-01(M=1 で約1.6万状態)から S3-06(約5千状態)へ変更。理由は、同期計算が長く vitest の RPC がタイムアウトしたため
3. 赤の起点: Q20 案aで全候補の (k0, a0) が同じになったため、`solve_for_candidates` の呼び出しは TS 側で不要になった(Rust 側の関数は残置)
4. `EvalContext` の分割: `ValuesContext` を新設
5. `EngineWorkerMessage`(Worker 応答に計測用の `meta` と、第15版で `fatal` を添える)を追加

## 6. 迷って止めた点・注意

- `npm test` の重い項目(A-5d 約13秒、A-4d S3-06 M=1 約11秒)。単独の `it` を30秒超にすると vitest の RPC がタイムアウトする
- `cargo test` は `[profile.test] opt-level=3` がないと数分かかる
- 測定はマシン負荷に依存する。M=1・2 は閾値を桁で超えるため判定には影響しない
- ベンチの headless Chrome が固まったときは、30分以上待たず、自分で起動したプロセスだけを PID 指定で停止する

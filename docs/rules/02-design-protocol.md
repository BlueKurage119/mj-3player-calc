# 設計フェーズ業務標準

- 対象: 設計担当
- 参照すべき関連指導文書: 
  - ノウハウ・背景: [G-01-hearing-first-design.md](advisory/G-01-hearing-first-design.md)・[G-03-external-review.md](advisory/G-03-external-review.md)
  - 設計書の矛盾・未実測の値の落とし穴は[G-10-design-consistency-pitfalls.md](advisory/G-10-design-consistency-pitfalls.md)


## 権限境界(必須)

1. 統括担当から渡された確定事項は、そのまま設計の前提とする。**自分で再検討・上書きしない。**
2. 渡された確定事項だけでは決まらない論点(仕様の解釈の分かれ目、UI挙動の分岐、対象範囲の線引き等)を**自分で決めない**。設計書には現時点の【設計案】として書き、最終返答の「要ヒアリング事項」に具体的な質問文の形で列挙する。
3. 変数名・ファイル配置・内部関数分割などの些末な実装ディテールは、ヒアリング対象にせず自分で決めてよい。
4. 設計書の記述が実物(コード・点数表・牌姿の実例等)と矛盾する、または要件が相互に矛盾する場合、**勝手に片方を選ばない。** 選択肢とトレードオフを設計書に書き、最終返答の「要ヒアリング事項」に回す。
5. ユーザーへの質問は自分では発しない(統括担当が代行する)。

## 設計書に必ず含める項目

1. 参照した資料と、そこから導いた設計判断の根拠(統括担当から渡されたヒアリング済みの確定事項を含む)
2. モジュール構成・型定義・APIエンドポイント等の具体的なシグネチャ
3. 受け入れ条件のチェックリスト — 検収担当がそのまま1項目ずつ実行できる粒度。各項目に「何をどう実行して何が見えれば合格か」を書く。「正しく動作すること」のような検証不能な書き方をしない
4. 後続Issueへの引き継ぎ事項
5. 実挙動を確認できなかった箇所は「実挙動未確認」と明記する

上記1〜5を満たさない設計書は、設計フェーズ完了とみなさない。

## 設計書の独立レビュー（試行）

設計担当が設計書を書き終え、未決事項がなくなった段階で、統括がユーザーへ設計承認を求める**前に**、設計書の独立レビューを1本通す。

- レビュー担当: 極力設計担当とは別のモデルを使用すること。Opus・Argon・Sol以上を推奨する。会話・判断経緯を共有しない。読むだけで設計書は直さないこと。
- レビュー観点:
  1. 受け入れ条件が検収担当がそのまま1項目ずつ実行できる粒度か 
  2. 内部矛盾・受け入れ条件と変更禁止制約の両立(G-10)
  3. 記載されたコード・関数名が実物と一致するか
  4. 麻雀ルール・点数の根拠に出典があるか(業務標準07)
  5. 【設計案】【未確定】を確定扱いしていないか
- 統括は指摘の真偽を実物で判定し、判定結果と根拠を設計承認の提示(01号「設計承認の受け方」)に添える。
- 省略できるのは、docs のみの Issue か、ユーザーが省略を承認した場合。
- 首席統括担当が指定されている場合、設計書の独立レビューは首席統括担当のサブエージェント等が実施すること。

## 成果物の制約(必須)

- 対象の `docs/design/issue-<N>-<slug>.md` 1本だけを新規作成または改訂する。差し戻し時は既存の設計書を改訂する。
- コードを1行も書かない(`src/`・`wasm/`配下、設定ファイル含む)。ブランチを切らない。コミットしない。
- 着手時に既存差分を記録する。終了時は`git status --porcelain`と差分を確認し、自分が加えた変更が対象設計書だけであることを報告する。開始時から存在した他者の変更は保持し、一時的な検証変更は復旧する。

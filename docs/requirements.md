## 1. 概要

- 【確定】三人麻雀に特化したスマホ向け点数計算機。Webアプリ(PWA)として配布し、オフラインでも全機能が動く
- 【確定】開発環境は React + Vite(TypeScript)
- 【確定】ライセンスは MIT。計算コアは livewing/mahjong-calc(MIT)から取り込む([license-policy.md](license-policy.md))
- 【確定】Version 1 のリリースを優先する。何切るの期待値計算(Epic F のフェーズ2)は v1 の後に回す

## 3. 機能要件

### 3.1 手牌の入力
- 【確定】パレット方式とテンキー方式(mj-mighty-calc 式)を併用する。切り替えても入力中の手牌は消えない
- 【確定】三麻で使わない牌(2m〜8m)は入力できない。同じ牌の5枚目は入力できない(赤牌を含めた枚数を管理する)
- 【確定】副露はポン・明槓・暗槓(加槓は明槓と同一扱い。入力上は区別しない。チーはない)
- 【確定】抜き北の枚数入力(北の扱いが「抜きドラ」のときのみ)
- 【確定】ドラ表示牌・裏ドラ表示牌。萬子は 1m→9m、9m→1m とめくる
- 【確定】和了牌は、手牌の最後の牌として指定する(mahjong-calc の方式)
- 【確定】ヘッダーの三点リーダーのメニューに「ランダム14枚」「ランダム清一色」を置く。手牌を門前14枚に置き換え、副露・ドラ・裏ドラ・抜き北を消す。卓の設定と状況役は残す。赤牌はルールの赤枚数に従う。清一色は筒子か索子(Issue #95)。

### 3.2 状況の入力
- 【確定】自風は東・南・西のみ。場風(東・南・西)
- 【確定】親か子かは自風から決まる(自風が東なら親)。独立した入力にしない(Issue #11)
- 【確定】立直、ダブル立直、一発、嶺上開花、槍槓、海底、河底、天和、地和
- 【確定】本場・供託。三麻の1本場あたりの点数は設定値にする

### 3.3 結果表示
| 牌姿 | 表示する内容 |
| --- | --- |
| 和了形 | 【確定】役一覧、翻・符、符の内訳、点数、ツモ時の支払いの内訳。ツモとロンは入力させず、結果側に並べて表示する |
| 聴牌形 | 【確定】待ち牌ごとの役と打点(ツモとロン)、残り枚数 |
| それ以外 | 【確定】向聴数、有効牌の種類と枚数、何切る |

### 3.4 何切る
- 【確定】フェーズ1(v1): 打牌候補ごとに向聴数、受け入れの種類と枚数を表示する。残り枚数は三麻の牌構成(108枚)と抜き北を前提にする
- 【確定】フェーズ2(v1 の後): 聴牌確率・和了確率・期待値。Web Worker で計算する。クリーンルームで独自実装する

### 3.5 ルール設定
| 項目 | 選択肢 |
| --- | --- |
| 赤ドラ | 【確定】赤なし／2枚(基準。5p・5s 各1)／4枚(5p・5s 各2)。全赤は採用しない |
| 数え役満 | 【確定】あり(基準)／なし |
| 切り上げ満貫 | 【確定】なし(基準)／あり |
| ツモ損 | 【確定】あり(基準)／北家分折半／ロン打点折半。端数処理は mahjong-rules.md §3.1 のとおり(Issue #13) |
| 北の扱い | 【確定】抜きドラ(基準)／共通役牌 |
| その他 | ルールの詳細は [麻雀ルール仕様](mahjong-rules.md) を正本とする |

- 【確定】ルールは柔軟に切り替えられるようにする
- 【設計案】よく使う組み合わせを名前付きのプリセットとして保存できる(Epic B では扱わず、後続の Epic で検討する)
- 【確定】設定は端末に保存する

## 4. 非機能要件

- 【確定】デザインは Material Design 3 Expressive に準ずる。Material Web で使えるものはラップ・改造して使い、使えない部分は自作する
- 【確定】PWA(vite-plugin-pwa)。WASM と牌画像もプリキャッシュする
- 【確定】点数計算は入力後すぐ(100ms 以内)に表示する。v2 で採用予定の何切る確率計算(mahjong-cpp 同等の機能。Issue #7 の F3)は対象外
- 【確定】タップ領域は原則 48dp 以上とする(本プロジェクトの設計方針。WCAG 2.2 は AA 24px・AAA 44px)。ただし入力欄の細部(ステッパーの増減ボタン等、画面幅の都合で入り切らないもの)に限り、目標 44dp・最低 40dp とする。隣接ターゲット間隔は 8dp 以上を維持する(Connected button group のピル内の隙間 2dp は例外)。牌パレット(底部シートの 9 列の牌キー。赤五筒・赤五索のボタンを含む)に限り、タップ領域を高さ 48dp・幅は 9 等分(375px 幅で約 36dp。最低 36dp)とする。この幅は WCAG 2.2 の AA(24px)を満たし、AAA(44px)は満たさない。この緩和は牌キーにだけ適用し、他の入力欄には広げない。ステッパーの緩和とは別枠とする。牌パレット全体(牌キー・赤ボタン・機能キー)は隣接ターゲット間隔 8dp の例外とし、列の間隔を 2dp、行の間隔を 4dp とする。機能キーは 2 列以上を占め、幅・高さとも 48dp 以上とする。360px 幅では牌キーの幅が約 34.7dp となり 36dp を下回るが、余裕の確認にとどめ、合格基準には含めない(Issue #46)。テンキー(底部シートの 4 列 × 5 行のキー)は隣接ターゲット間隔 8dp の例外とし、キーの間隔を 4dp とする。キーの大きさは高さ 48dp・幅は 4 等分(375px 幅で約 82dp)とする(Issue #47)。手牌・ドラ・裏ドラ・副露の各カードのゴミ箱(手牌クリア・表示牌クリア・副露の削除)に限り、タップ領域を高さ 24dp(見た目と同じ。縦は拡張しない)・幅 40dp(最低 32dp)とする。この大きさは WCAG 2.2 の AA(24px)を満たし、AAA(44px)は満たさない。誤操作を防ぐため、ゴミ箱の左と下に 8dp の無反応帯(押しても何も起きない領域)を置く。ゴミ箱の上と右は各カード本体のタップ領域(シートを開く)と 0dp で隣接し、隣接ターゲット間隔 8dp の例外とする。この緩和は各カードのゴミ箱にだけ適用し、他の入力欄には広げない(Issue #55・#48)。手牌カードの牌(タップで選択、もう一度のタップで削除)に限り、タップ領域を牌の見た目と同じ大きさとする(375px 幅・14枚で幅約 21.9dp・高さ約 29.1dp)。この幅は WCAG 2.2 の AA(24px)を満たさない。牌の間隔は 1dp とし、隣接ターゲット間隔 8dp の例外とする。誤操作は2段階の操作(選択→削除)で防ぐ。結果欄の本体の牌(聴牌・向聴の待ち牌・有効牌、何切るの打牌候補)に限り、タップ領域を牌の見た目と同じ大きさとする(待ち牌・有効牌は幅 24dp・高さ 32dp、打牌候補は幅 36dp・高さ 48dp)。枚数表示はタップ領域に含めない。隣接ターゲット間隔は 8dp 以上を維持する(待ち牌・有効牌は縦 8dp・横は枚数表示を挟んで約 34dp、打牌候補は縦約 39dp)。これらの緩和は手牌と結果欄の本体の牌にだけ適用し、他の入力欄・バナーの牌には広げない(Issue #89)。牌・数値の入力(パレット・テンキー・状況役)は底部シートで行い、片手で操作できるようにする
- 【確定】画面幅は 375px 以上を対象(推奨幅)とし、320px は非推奨とする
- 【確定】品質チェックは Biome(lint・format)、tsc(型検査)、Vitest(テスト)。GitHub Actions の CI で実行する
- 【設計案】点数・役・符はゴールデンテスト(出典付きの期待値)で担保する。取り込んだ mahjong-calc はテストが牌ユーティリティのみのため、改修前に整備する

## 5. 既知の改修ポイント(調査済み)

- 【確定】手牌分解器(Rust)は34種の枚数配列を受け取るだけで、牌の種類を知らない。2m〜8m を0枚にすれば無改修で三麻の手牌を分解できる(テストで確認済み)。ただし入力を検証しないため、牌セットの保証は TS 側の責任
- 【確定】`shantenTiles`(浮き牌の前後2枚)と`chitoitsuShantenTiles`(34種を列挙)は、2m〜8m を有効牌に含めてしまう。除外が必要
- 【確定】四麻前提の箇所: 自風に北家がある、支払い計算が4人払い前提、残り枚数が全種類4枚前提、ドラ表示牌の「次の牌」
- 【確定】mahjong-calc の localStorage 復元にはマイグレーションがない。Rule・Input を拡張するときに対応が必要

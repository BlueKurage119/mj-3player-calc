### 1.2.1 参考の事実

- 取り込み元(`../ref-repo/mahjong-calc` の 6550200。統括担当が確認)の `uniqueHoras` は本リポジトリの現状と同じ比較で、同点時の決めを持たない。分解器も `HashSet` のまま。よって本 Issue の揺れは取り込み元由来であり、取り込み元に合わせるべき既定の挙動は無い。

### 1.3 現状の問題(コード調査の事実)

現行の比較(和了牌・ツモ/ロンが同じ候補間)は次の通り。

1. どちらかが役満 → 役満の倍数の降順だけを返す(同倍数なら 0)。
2. どちらかが5飜以上 → 飜数の降順だけを返す(同飜なら 0)。**符で決まらない**。`1112223337899p` の件はこの経路(両形とも同じ飜数。5章の実測値)。
3. それ以外 → `calculateBasePoint`(内部で符を10符に切り上げ)の降順、最後に飜数の降順。生の符 38 と 40 は同点になる。R19 の件はこの経路。

いずれも同点が 0 で終わり、安定ソートで分解器の出力順(`HashSet` の反復順。実行履歴で変わる)が残る。

- 本プロジェクトのルール正本(`docs/mahjong-rules.md`)・要件(`docs/requirements.md`)には、「高点法(打点の最も高い解釈を採る)」の一般規定は無い(「高点」の検索0件)。近い記述は `docs/mahjong-rules.md` 125行付近(一色三順と三暗刻+三連刻に限った「打点の高い読み方を採る」)だけである。

## 2. 変更内容

### 2.1 `uniqueHoras` の比較順(全経路共通)

シグネチャは変更しない: `export const uniqueHoras = (horas: Hora[], rule: Rule): Hora[]`

比較関数を次の順の多段比較に置き換える。各段で差があればそこで返し、0 なら次の段へ進む。

| 段 | キー | 向き | 備考 |
| --- | --- | --- | --- |
| 1 | 和了牌 `compareTiles` | 昇順 | 現行どおり(グループ化のため) |
| 2 | `by` | ron → tsumo | 現行どおり |
| 3 | 役満の倍数 `yakumanMultiplier(yaku, rule.multipleYakuman)` | 降順 | 役満でない候補は 0 として扱う。役満と非役満の混在でも役満が先頭(現行と同じ結果) |
| 4 | 基本点 `calculateBasePoint(生の符, 飜, rule.roundedMangan, false)` | 降順 | 両方とも役満でないときだけ比べる |
| 5 | 飜数(`yaku` の `type==='yaku'` の `han` 合計。現行と同じ数え方) | 降順 | 両方とも役満でないときだけ。確定事項1 |
| 6 | 生の符(`mentsu` は `sumOfFu(fu)`、それ以外は 25。現行と同じ) | 降順 | 両方とも役満でないときだけ。確定事項1 |
| 7a | 待ちの順位 | 昇順 | 3.2。単騎=0 → 嵌張=1 → 辺張=2 → 双碰=3 → 両面=4、待ちなし=5 |
| 7b | 正準文字列 | 文字コード昇順 | 3.3 |

要点:

- 「5飜以上なら飜数だけ」の早期 return を廃止する。満貫以上は `calculateBasePoint` が飜数だけで決まるので、段4で同点 → 段5(飜数)→ 段6(生の符)の順に流れる。これで `1112223337899p` が段6で三暗刻側(生の符が高い)に決まる。
- 段4は現行の `calculateBasePoint` の呼び出しをそのまま使う(5飜以上も含めて呼んでよい。満貫以上は符によらない値を返す)。
- 役満同士で倍数が同じ場合は、役満の打点が倍数だけで決まるので、段4〜6は比べず段7aへ進む。非役満の飜数・符を役満の比較に混ぜない。
- 段7まで入れると、比較関数は「和了牌・by が同じで内容まで完全に同じ」候補どうしでだけ 0 を返す。その場合はどちらを残しても表示は同じ。各段は単純な数値差・文字列比較で返し、推移的な全順序にする。

## 3. 段7(最終の決め)の定義(確定: 案A)

### 3.1 必要な理由

段6まで同じでも表示が違う分解は実在する(レビュー担当の実測。設計担当は未実行):

- `678p777p22p67s888s` + `8s` ツモ: 双碰待ちの分解と両面待ちの分解がともに2飜・生の符 30。案Aでは双碰が残る。

段7が無いと、こうした手で実行履歴により表示が揺れる。

### 3.2 段7a: 待ちの順位

`hora.ts` 内に非公開の関数を置く。

```ts
const waitingRank = (h: Hora): number
```

- `h.type === 'mentsu'` のとき: `h.fu` から `type === 'waiting'` の要素を探し、その `waitingType` を順位に変換する。`tanki`=0、`kanchan`=1、`penchan`=2、`shampon`=3、`ryammen`=4。
- 待ちの要素が無い `mentsu` 和了と、`chitoitsu`・`kokushi`・`shisanputa`(待ちを持たない和了)は 5 とする。
- 比較は `waitingRank(a) - waitingRank(b)`(小さい方が先頭)。
- 待ちなし=5 が `mentsu` 和了との比較で効くのは、**役満の倍数が同じときだけ**である。役満でない場合は、`Fu` 型の `fu` が偶数のリテラル型だけで、`mentsu` の `sumOfFu` は 25 になり得ないため、`chitoitsu` 等(25扱い)と `mentsu` は段6までに必ず決まる。

### 3.3 段7b: 正準文字列

```ts
const canonicalKey = (h: Hora): string =>
  JSON.stringify([
    h.type,
    h.type === 'mentsu' ? h.melds : [],
    h.type === 'mentsu' ? h.fu : [],
    h.yaku
  ]);
```

- 和了牌と `by` は段1・2で一致しているので含めない。
- 比較は `ka < kb ? -1 : ka > kb ? 1 : 0`(UTF-16 コード単位の順)。`localeCompare` は環境で順序が変わりうるため使わない。
- `JSON.stringify` のプロパティ順は、各オブジェクトの生成箇所のリテラルの順で固定される。値の並び替え(キーのソート等)はしない。
- 事前計算(`Map` へのキャッシュ)は製造担当の任意とする(候補数は高々数十件)。
